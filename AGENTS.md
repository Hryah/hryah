# Вхід для розробників і AI-агентів

hryah — браузерна гра для NASA Space Apps 2026 (TypeScript, React, Vite). Цей файл містить чинні рішення та коротку передачу роботи; історія змін живе в `docs/DEVLOG.md`.

## Перед роботою

1. Перевір `git status`, поточну гілку й реальний код: опис не доводить, що зміна вже злита або опублікована.
2. Прочитай `docs/ROADMAP.md`, останній запис `docs/DEVLOG.md`, `docs/ARCHITECTURE.md` і `REVIEW_RULES.md`.
3. Для логіки прочитай `src/core/contracts.ts` (джерело правди) і `src/core/stub-phases.ts` (зразок Phase).
4. Прочитай вкладені `AGENTS.md` у своїй ділянці. Інструкції доступні з нового клону; доступ до акаунтів, дозволи та локальні файли автоматично не переносяться.

## Затверджена гра

- Основний режим: кампанія агенції — кілька запусків поспіль, кожен із яких це проєктування → політ → орбіта → причинний розбір і виплата. Цикл живе в кімнаті консорціуму; соло це кімната з ботами. Напрям і стан хвиль: `docs/EXPANSION.md`.
- ПК, WASD + E; миша для пультів. Ціль відображення: справжня 3D-кімната й обладнання, мальований 2D-космонавт на прозорій площині, фіксована ортографічна ізометрія з камерою, що слідує за ним.
- Космонавт: `art/astronaut/source/`; основний передній вид — `front.svg` («космонавт перед (2).svg»), ще три напрямки — back/left/right. Оригінали не змінювати. Підготовлені текстури та анімації — окремі похідні ресурси.
- Спочатку проста кімната, рух, зіткнення й один пульт. Складну інерцію, поручні, EVA та повні мініігри додаємо після цього. Наявну логіку польоту адаптуємо, а не переписуємо.
- Three.js дозволений лише в шарі відображення. GLB — для світу й обладнання; персонаж залишається мальованим.

## Межі та архітектура

Локальна правка в `feature/oleksii-render` поверх `0220f56`: виправлено JSON після злиття; `StageCanvas.active` паузить сцени й відкладає створення WebGL до першого показу; помилки монтування звільняють ресурси. `setBeam` сам відновлює видимість. Типи, 326 Vitest + 3 Node тести й збірка пройшли; ручне перемикання екранів ще не перевірене. Зміни закомічено у feature/oleksii-render (PR #31); у experimental і на Pi їх ще немає; наступна перевірка цієї правки — пауза/відновлення сцен у браузері.

- Звичайна ділянка фази: `src/core/<design|flight|orbit>/`, відповідна `src/ui/…/` і підключення в `src/core/phases.ts`.
- Спільні `contracts.ts`, `game.ts`, `physics.ts`, `stubs.ts`, чужі фази, CI та деплой змінюй лише в межах прямо погодженого завдання. Не обходь контракт через `any` чи дубль типу. Зміни контрактів — окремий малий PR для інтегратора, спочатку зворотно сумісні.
- Roadmap задає напрям, але не означає, що всі етапи вже реалізовано. Нові ігрові правила поза ним погоджуй; дрібні зворотні рішення приймай сам і вкажи у звіті.
- Phase зберігає `init / step / isDone / finish` і `debugActions`. React/Three читають стан і надсилають дії; координати камери не визначають правила руху, задач чи ресурсів.
- `step` не мутує вхід. Стан — звичайні JSON-дані без класів, Map/Set, функцій чи значень undefined. Час надходить дією `tick`, випадковість — через `nextRandom(rngState)`.
- Одиниці в назвах полів (`massKg`, `chargeWh`, `dtS`). Кожна відмова має унікальний `CauseEntry.id`, `kind: 'failure'` і непорожній `causedBy`. `finish().log` повертає лише нові записи фази.
- Тексти гравця — ключі й англійський словник; UI не рахує правила гри. Сховище — через `src/storage.ts`.
- При інтеграції: виробничий дефект застосовується до специфікації один раз; політ повертає лише нові пошкодження. `FlightResult.deploymentStatus?: 'deployed' | 'lost'`: відсутнє поле зберігає стару поведінку, лише lost оминає орбіту й дає невдалий розбір. GAME_OVER/VICTORY завершують фазу, термінальні стани не приймають нових дій.
- SAFE в першій версії: камера й передача не працюють, доступний обігрів дозволений, базове споживання не зменшується. Локально `netPowerW` узгоджено з цим правилом (MODEL D9); заглушка орбіти перевіряє фактичну висоту місії.

### Сцени рушія відображення

Якщо завдання про вигляд частини, спершу прочитай `docs/RENDER_GUIDE.md`. До дозволених файлів твоєї частини додаються:

- `src/scenes/<частина>-scene.ts` — твоя сцена;
- `src/scenes/views.ts` і `src/scenes/views.test.ts` — лише твій вид, функція «стан → вид» і відповідні тести;
- `src/scenes/gallery.tsx` — лише запис твоєї сцени;
- `src/data/sprites.json` і `public/assets/sprites/` — записи й файли твоїх спрайтів;
- `src/data/texts.en.json` — лише нові ключі.

Сам рушій (`src/render/`), `src/scenes/types.ts` і чужі сцени змінюй лише в межах прямо погодженого завдання. Якщо в рушії чогось бракує, зупинись і скажи людині.

## Перевірки й передача

```sh
npm ci
npm run typecheck
npm test
npm run build
npm run assets:prepare
npm run assets:check
node art/astronaut/validate-sources.mjs
node tools/asset-workshop/scripts/reproduce.mjs
```

`assets:prepare` відтворює чотири прозорі SVG та копію GLB-пульта; `assets:check` перевіряє оригінали, похідні файли й тести підготовки та автоматично запускається перед `npm test`. Тести Node для SVG відокремлені від Vitest. Майстерня має власний package/lockfile; root-тести не потребують її залежностей. Джерела → згенеровані ресурси → зібрана майстерня/повний ZIP → `nikita models/`. Деталі — `tools/asset-workshop/README.md`. Не редагуй зібрані bundles вручну.

Для змін логіки перевір чистоту, детермінізм, JSON round-trip, прохід init→finish, успіх/провал і причинний журнал; `src/core/game.test.ts` має лишитися зеленим. Для графіки перевір у браузері прозорість, масштаб, перекриття та реальні анімації. Статичні пози не називай циклом бігу. Не послаблюй чужі тести заради зеленого результату.

CI шукає заборонені звернення в ядрі навіть у коментарях: DOM/сховище/годинник, `Math.random`, імпорти React/Three/Pixi/Zustand. `noUncheckedIndexedAccess` вимагає перевірки індексованих значень. Імпорти TS без розширення.

Після кожної завершеної зміни/PR онови цей короткий стан, ROADMAP і DEVLOG: що, навіщо, інтерфейси, перевірки, гілка/коміт, обмеження, **одне наступне завдання**. Не зберігай секрети, абсолютні шляхи конкретного ПК або залежність від цього чату.

## Git і звіт

- Працюй у `feature/*`; малі змістовні коміти й PR до `experimental`. Без прямого push/merge до `experimental` або `main`, без force та переписування історії. Публікація: `experimental`, потім `main` за `CONTRIBUTING.md`; майстерня має окремий сайт.
- Нові залежності додавай у межах погодженого завдання; майстерня ізольована від пакета гри. Секрети не коміть.
- Чинний `ci-cd.yml` при ручному workflow_dispatch надсилає Telegram команді навіть із feature-гілки. Без прямого доручення надсилати повідомлення використовуй локальні перевірки або CI події pull_request; ручний workflow не запускай.
- Наприкінці коротко українською: результат, змінені ділянки, перевірки, прийняті рішення, обмеження та наступний крок. Не заявляй перевірок, яких не запускав.
