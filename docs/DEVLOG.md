## 2026-11-15 — P0: місійний профіль енергії та metadata вантажу

**Статус: локально в `feature/nikita-orbit-model`, база b9a0cbb; залежить від відкритого PR #64. Пакет входить до model-коміту з цим записом; ще не відправлено. Merge/auto-merge не виконувалися.**

`src/core/model/orbitEnergy.ts` експортує чисті `orbitProfile(mission, orbitIndex)` і `orbitGeneratedMb(profile, rateMbps, elapsedS, cameraOn)`. Профіль серіалізується в JSON, нумерація витка з 1. Flyby вимикає зйомку поза включними межами, зберігаючи тривалість усіх відрізків. Cargo навантажує весь виток одним instrumentW, автоматично формує обмежений звіт і очищує невідправлений буфер після pass. Прогноз energy враховує накопичений дефіцит, фактичну тривалість передачі та номінальне блокування холодом для нових цілей; бурі й пошкодження залишаються поза preflight. Старі виклики segmentLoadW без профілю та місії без objective зберігають числову поведінку.

`src/core/model/spec.ts` копіює cargoKind тільки за наявності каталожного metadata, без виведення з id. Новий cargo link margin вимагає розмір звіту, а не уявний обсяг фото; нові цілі використовують доступну тривалість pass. `src/data/orbit-rules.json` перенесено з погодженого ТЗ, зокрема cold-пороги читає модель. Додано 21 тест у `src/core/model/orbitEnergy.test.ts`: межі вікна, аналітичні Wh, всі п’ять навантажень, expiry/cold, слабкі панелі, частковий буфер, metadata чотирьох контейнерів, чистота/детермінізм/JSON, link margin. Старі balance/sweep тести не послаблено.

**Перевірки:** фінальний npm run typecheck пройшов; цільовий прогін двох model-файлів — 48 тестів; npm test — 45 файлів / 499 Vitest + 3 Node через pretest assets:check; npm run build, core purity за шаблоном CI й git diff --check пройшли. Попередження Vite про великий чанк і Vitest про майбутній native config loader лишилися. UI/ресурси не змінені, браузер не перевірявся.

**Обмеження:** orbit-фаза ще не читає нові цілі; missions.json не активує жодного objective, тому ця зміна готує модель, а не готовий місійний gameplay. contracts.ts не змінений у цьому пакеті. ## 2026-11-15 — інформаційні вікна між фазами кампанії

**Гілка: `feature/illia-phase-cards`, база `b3483bc`. Злиття й публікація не підтверджені.**

P0 від Ашота: перед кожною фазою й після неї має бути стилізований підсумок у спливаючому вікні з простим переходом. Вікно пояснює, що робити на наступному етапі, і навіщо так роблять справжні місії.

Шаблон `src/ui/campaign/PhaseCard.tsx` один на всі переходи. Тексти лежать у ключах `ui.card.<id>.{kicker,title,next,why}`. Рядки підсумку передає виклик. Є місце під ілюстрацію 3:2: готовий файл вписують у `ART` у `PhaseCard.tsx`. Поки ілюстрацій немає, блок не рендериться. `orbitCargo` бере ілюстрацію `orbit`, `lost` бере `report`. Прапорець «Don't show these windows again» зберігається через `storage.ts`. Увімкнути вікна знову можна кнопкою «Phase windows» під панеллю кампанії.

Переходи:
- **`window`:** початок вікна для агенції гравця. Показує підсумок минулого вікна, прогрес програми й брифінг. З'являється раз на агенцію й вікно; у грі за одним екраном кожна людина бачить своє.
- **`launch`:** після запуску. Показує масу, Δv, носій і вартість. Політ реального часу монтується лише після закриття вікна.
- **`orbit` / `orbitCargo`:** після польоту. Показує досягнуту орбіту, залишок пального й пошкодження.
- **`report`:** після дограної орбіти. Показує результат, дані й витки; кнопка вікна надсилає звіт.
- **`lost`:** апарат втрачено. Кнопка надсилає звіт, повтор після мережевого збою працює як раніше.

Ядро й контракти не змінені. Кімнати без кампанії вікон не показують.

**Перевірки:** `npm run typecheck`, 478 Vitest (нові `cards.test.tsx`: усі ключі текстів; вікно запуску відкривається до монтування польоту). Браузерний прохід соло-кампанії в headless Chromium: window → launch → політ → orbit → 10 витків → report → вікно 2 з підсумком вікна 1; після «Wait a turn» вікно не з'являється знову. Firefox і Safari не перевірялись.

**Наступне одне завдання:** вставити ілюстрації художників у `public/assets/cards/` (window, launch, orbit, report).

- Політ уже містить фізику невагомості, поручні, зіткнення, пульти, кризи та мініігри. Наявну роботу адаптуємо замість повторної реалізації. Рендер польоту й переглядач GLB використовують Canvas 2D; справжнього 3D-світу з авторським 2D-персонажем ще немає.
- `FlightResult` містить орбіту, залишок палива й пошкодження, але не статус відділення або втрати. Виконавець завжди переходить до орбіти після завершеного польоту; `GAME_OVER` сам не встановлює `phaseDone`. Це завдання інтеграції етапу 2.
- Консорціум, його аналіз і `sim.ts` використовують заглушки. Виробничий дефект уже застосовується до специфікації один раз; нові пошкодження польоту мають передаватися окремо.
- Чинний SAFE орбіти вимикає камеру й передачу, дозволяє доступний обігрів і не зменшує базове споживання. Допоміжний `netPowerW` має суперечливе правило; відкрита розбіжність D9 описана в [MODEL.md](MODEL.md).
- `src/storage.ts` має JSON-збереження з префіксом каналу, але збереження забігу `#play` і версія формату ще не підключені.
