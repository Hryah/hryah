# План рушія відображення (2.5D)

> Статус: план від 14.11, 14:00. Адресат: Claude Code, який веде цю роботу разом з Олексієм. Перед початком прочитай `AGENTS.md`, `docs/ARCHITECTURE.md` і `docs/MECHANICS.md`.

## 1. Навіщо це

Гра має логіку (ядро в `src/core/`), але на екрані досі лише дебаг-кнопки. Попередня спроба графіки дала статичну сторінку. Причина не в мові, а в тому, що не було головної ознаки гри: **циклу кадрів**.

Сторінка перемальовується, коли змінюється стан. Гра перемальовується щокадру, навіть коли стан не міняється: супутник пливе по орбіті, шкала плавно доганяє нове значення, пульт блимає. Увесь рушій побудований навколо цього.

## 2. Що таке 2.5D у нас

- **Світ тривимірний і написаний кодом:** планета, орбіта, тінь, зоряне тло, стенд, відсік корабля, пульти. Лише примітиви Three.js, без файлів моделей.
- **Об'єкти двовимірні й намальовані:** апарат, його модулі, оператор, іконки подій. Це спрайти (PNG з прозорістю), які колеги малюють окремо. У сцені вони стоять як площини, завжди повернуті до камери.
- **Камера ортографічна й нерухома.** Гравець її не крутить. Саме це дає 2.5D: об'єм і глибина є, перспективи немає, спрайти малюються під один ракурс.

## 3. Рішення, які вже прийняті

| Питання | Рішення | Чому |
|---|---|---|
| Бібліотека | `three` (і `@types/three`), більше нічого | справжній рушій із циклом кадрів; без додаткових шарів |
| React Three Fiber | не беремо | зайвий шар абстракції; цикл кадрів простіше тримати явно |
| Моделі з Blender, GLB | не беремо | немає часу на конвеєр ресурсів |
| Власний GLB-парсер із гілки `sasha-design` | не зливаємо | це самописний рендерер замість рушія |
| Реєстр «id → вигляд» із тієї ж гілки | ідею беремо | стає маніфестом спрайтів (розділ 6) |
| Фізичний рушій | не беремо | фізика гри рахується в ядрі; сцені потрібні лише плавні переходи |
| Взаємодія | звичайні HTML-кнопки поверх полотна | кліки по 3D-об'єктах дорогі й ненадійні |

Залежності додає лише Олексій окремим малим PR.

## 4. Три шари

```
стан ядра  →  вид (чиста функція)  →  сцена (цикл кадрів)
GameState     OrbitView, DesignView    Three.js
```

1. **Стан ядра.** Вже є. Рушій його лише читає.
2. **Вид.** Чиста функція «стан → що треба показати»: кут супутника на орбіті, частка заряду, які модулі стоять, які тривоги активні. Жодного Three.js. Лежить у `src/scenes/views.ts` і тестується звичайними тестами.
3. **Сцена.** Щокадру отримує останній вид і час кадру. Сама нічого не вирішує, тільки плавно наближає картинку до виду й додає власний рух (обертання планети, мерехтіння).

Чому вид окремо: його можна перевірити без браузера, а сцену можна дивитись на вигаданих даних, не граючи в гру.

## 5. Структура файлів

```
src/render/                 рушій, нічого не знає про гру
  stage.ts                  полотно, ортографічна камера, зміна розміру, цикл кадрів
  palette.ts                кольори й готові матеріали
  sprites.ts                маніфест, фабрика спрайтів, заглушка для відсутнього файла
  motion.ts                 плавне наближення до цілі, пульсація, рух по колу
  primitives.ts             планета, кільце орбіти, сектор тіні, зорі, коробка пульта
  StageCanvas.tsx           React-обгортка: монтує сцену, передає їй вид
src/scenes/
  types.ts                  інтерфейс сцени
  views.ts                  чисті функції «стан → вид» з тестами
  orbit-scene.ts            частина 3
  design-scene.ts           частина 1
  flight-scene.ts           частина 2
  gallery.tsx               перегляд сцен на вигаданих даних
src/data/sprites.json       маніфест спрайтів
public/assets/sprites/      файли від колег
```

`src/core/` не чіпаємо. `src/render/` не імпортує нічого з `src/core/`, окрім типів у `views.ts`.

### Інтерфейс сцени

```ts
export interface Scene<View> {
  mount(stage: Stage): void;                          // створити об'єкти один раз
  update(view: View, dtS: number, timeS: number): void; // щокадру
  dispose(): void;                                    // прибрати за собою
}
```

`update` не створює нових об'єктів і матеріалів, лише міняє наявні. Усе створюється в `mount`.

## 6. Спрайти

Маніфест `src/data/sprites.json` зв'язує id із ядра (ті самі, що в `catalog.json`) з файлом:

```json
{
  "cam-m": { "file": "modules/cam-m.png", "widthUnits": 1.2, "anchor": [0.5, 0.0] },
  "bus":   { "file": "spacecraft/bus.png", "widthUnits": 2.0, "anchor": [0.5, 0.5] }
}
```

Правила:

- **Файла може не бути.** Тоді `sprites.ts` малює заглушку: кольоровий прямокутник із підписом id. Гра завжди відмальовується, спрайти підкладаються пізніше без змін у коді.
- **Апарат збирається зі спрайтів.** Корпус має точки кріплення для п'яти слотів; модуль ставиться у свою точку з невеликим зсувом у глибину.
- **Розмір задається у світових одиницях,** а не в пікселях.

Вимоги до спрайтів для колег (покласти окремим коротким файлом `docs/SPRITES.md`):

- PNG із прозорим тлом, довша сторона 512 px;
- ракурс: вигляд спереду трохи згори, світло зліва згори;
- кольори лише з палітри (`palette.ts`), темний контур 4–6 px;
- назва файла дорівнює id модуля.

## 7. Палітра і вигляд

Один файл `palette.ts`, з якого беруть кольори і сцени, і ті, хто малює спрайти:

- тло космосу, зорі;
- планета (день, ніч), атмосфера;
- корпус, панелі, метал;
- акцент (активне), тривога (відмова), спокій (норма).

Правила вигляду:

1. плоске затінення, контури по ребрах для кодових об'єктів;
2. одне спрямоване світло і м'яке розсіяне, без тіней;
3. жодного кольору, заданого прямо в сцені;
4. усе повільно рухається: нерухомий кадр вважається помилкою.

## 8. Сцени

| Сцена | Що в ній | Що рухається |
|---|---|---|
| Орбіта | планета, кільце орбіти, сектор тіні, станція на поверхні, апарат | апарат по орбіті; планета обертається; апарат темніє в тіні; промінь до станції під час сеансу; спалах під час бурі |
| Проєктування | стенд, корпус апарата, модулі в точках кріплення | модуль плавно з'являється при виборі; апарат погойдується; червоний запас підсвічує відповідний модуль |
| Політ | відсік у розрізі, чотири пульти, оператор | оператор переходить до пульта; пульт із задачею блимає швидше ближче до дедлайну |

Порядок: орбіта, проєктування, політ. Орбіта перша, бо найпростіша й найефектніша, а ядро частини 3 з'явиться найближчим.

## 9. Як перевіряти

Сторінка зі статичним кадром не вважається зробленою. Для кожної сцени:

- **Галерея.** `#gallery` показує сцену на вигаданому виді, який сам змінюється в часі. Розробляти й дивитись сцену можна без гри.
- **Два знімки.** Зроби знімок екрана на 1-й і на 4-й секунді. Вони мають відрізнятись. Подивись на них сам, перш ніж казати «готово».
- **Тести виду.** Для `views.ts` звичайні тести: стан на вході, очікуваний вид на виході.
- **Запасний шлях.** Якщо WebGL недоступний, `StageCanvas` показує текст із поясненням, а не порожнє місце.
- Звичайні перевірки з `AGENTS.md`: `npm run typecheck`, `npm test`, `npm run build`.

## 10. Порядок робіт і розподіл

Етап 0 робиться послідовно й одним виконавцем. Далі сцени можна роздати субагентам паралельно, бо вони залежать лише від рушія.

| Етап | Що | Готово, коли |
|---|---|---|
| 0. Рушій | `three` у залежностях, `stage`, `palette`, `motion`, `sprites` із заглушками, `StageCanvas`, порожня галерея | у галереї крутиться тестовий куб і стоїть спрайт-заглушка |
| 1. Орбіта | `OrbitView`, `orbit-scene`, запис у галереї | апарат проходить виток за 20 с, темніє в тіні, є промінь до станції |
| 2. Проєктування | `DesignView`, `design-scene`, підключення до екрана частини 1 | зміна модуля в грі міняє апарат у сцені |
| 3. Підключення орбіти | сцена орбіти читає стан справжньої частини 3 | тумблери й події видно в сцені |
| 4. Політ | `FlightView`, `flight-scene` | задачі на пультах і оператор видно в сцені |
| 5. Спрайти | файли колег замість заглушок | жодної заглушки на знімках |

Правила для паралельної роботи:

- до кінця етапу 0 ніхто, крім його виконавця, не пише в `src/render/`;
- після етапу 0 інтерфейси `Stage` і `Scene` міняються лише через Олексія;
- кожна сцена йде окремим малим PR в `experimental`;
- `package.json` чіпає тільки Олексій.

Орієнтири за часом: етапи 0 і 1 сьогодні до вечора, етап 2 сьогодні вночі або в неділю зранку, етапи 3–5 у неділю до обіду. Після обіду неділі нових сцен не починаємо.

## 11. Чого не робимо

- керування камерою, масштабування, обертання сцени мишею;
- тіні, відбиття, постобробка;
- анімація спрайтів по кадрах (лише зсув, масштаб, прозорість, колір);
- звук;
- завантаження зовнішніх моделей і текстур планет.

Усе це можна додати після здачі, якщо лишиться час.
