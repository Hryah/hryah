# Частина 3. Орбіта: змусити супутник відпрацювати

Статус: запропоноване завдання для реалізації MVP, 14.11.2026.
Власник: група 3 / розробник `orbit`. Конкретного учасника команда призначає окремо.
Документ описує бажану поведінку; відповідного геймплею в `experimental` ще немає.

## 1. Короткий опис для команди

Гравець отримує супутник, який сам спроєктував і доставив на орбіту.
Тепер потрібно протриматися десять витків і передати на Землю потрібні дані.
Перед кожним витком гравець обирає, які системи працюватимуть: камера,
передавач, обігрів чи безпечний режим. Камера наповнює пам'ять, передавач
звільняє її, обидва споживають енергію. У тіні панелі не заряджають батарею,
а під час сонячної бурі генерація та зв'язок слабшають.

Головне рішення: **зібрати більше даних зараз чи зберегти апарат і передати
те, що вже є**. Наслідки залежать від вибору модулів у першій частині та
пошкоджень у другій. Після завершення показуємо результат і ланцюжки причин.

## 2. Межі першої версії

- Один супутник, одна незмінна орбіта, один наземний пункт зв'язку.
- Покроковий режим: один хід дорівнює одному повному витку.
- Кількість ходів беремо з `mission.durationOrbits`; зараз у місії це 10.
- Орієнтир тривалості цієї частини для гравця: 2–3 хвилини.
- Чотири тумблери, кнопка `Next orbit`, прогноз найближчого витка.
- Зйомка, сеанс зв'язку, тінь і одна прогнозована сонячна буря.
- Перемога або пояснений провал із переходом до загального розбору.

Рух космонавта належить до частини 2. Дозаправка, ремонт у відкритому космосі,
зміна орбіти, кілька супутників і мережевий мультиплеєр — наступні версії.

## 3. Що бачить гравець

```text
ORBIT OPERATIONS                  Orbit 4 / 10
Earth observer                    Target: 10,000 Mb

Battery      38 / 60 Wh            Stored       2,880 / 4,000 Mb
Delivered    2,880 / 10,000 Mb      Thermal      Stable

[ON ] Camera     [ON ] Transmitter
[ON ] Heater     [OFF] Safe mode

NEXT ORBIT
Sunlight → Imaging → Ground pass → Eclipse
Solar storm: no
Forecast: battery 39 Wh, delivered +3,840 Mb, lost 0 Mb

[ Next orbit ]

Last orbit: memory full; 320 Mb discarded.
```

Це схема розташування, не контрольний числовий сценарій.
Числові приклади для перевірки наведено в розділі 9.

Потрібні елементи екрана:

- Видимі лічильники витків, заряду, пам'яті та вже переданих даних.
- Ціль місії та якість знімка: відповідає вимозі чи ні.
- Чотири тумблери й одна основна кнопка завершення ходу.
- Послідовність подій наступного витка та попередження про бурю.
- Прогноз заряду після витка, передачі даних, переповнення й ризику втрати живлення.
- Короткий журнал останнього витка; попередження пояснюється текстом, не лише кольором.
- На завершенні — підсумок та кнопка переходу до розбору / нового забігу.

UI-тексти англійською, через `texts.en.json`. Схему й тумблери можна зробити
звичайними React-компонентами; готовність 3D-графіки не блокує MVP.

## 4. Тумблери

### Camera

Дозволяє зйомку лише у вікні зйомки. Поза ним камера автоматично не працює
і не споживає `instrumentW`. Увімкнення означає дозвіл автоматичному розкладу,
а не безперервну роботу протягом усього витка.

Камера додає дані в буфер зі швидкістю `instrumentRateMbps`.
Переповнення відкидає нові дані; вже збережені дані залишаються.
Зйомка при повному буфері все одно витрачає енергію до кінця вікна.

### Transmitter

Дозволяє передачу лише під час прольоту над станцією.
Передає наявні дані зі швидкістю `downlinkMbps`, витрачаючи `transmitterW`.
Коли буфер порожній, автоматично вимикається до наступного сеансу.
Зараховуються лише фактично передані дані, а не всі зняті.

### Heater

Дозволяє обігрів під час тіні з витратою `heaterW`.
Для MVP використовуємо умовний показник холодового стресу `coldStress` від 0 до 2,
без заяви про фізичне моделювання температури:

- після повної тіні без обігріву додається 1, максимум 2;
- після повної тіні з працездатним обігрівом віднімається 1, мінімум 0;
- при значенні 2 камера недоступна на наступному витку;
- після відновлення нижче 2 камера знову доступна; заблокований тумблер не скидаємо.

Передавач працює і при холодній камері: гравець може передати накопичене.
Стрес сам по собі не завершує місію. Вимкнення обігріву на один виток —
допустимий ризик, який економить енергію.

### Safe mode

На цей виток примусово вимикає камеру й передавач, вмикає доступний обігрів.
Базове споживання `baseLoadW` зберігається, панелі заряджають батарею.
Налаштування трьох інших тумблерів запам'ятовуються й відновлюють дію
після вимкнення безпечного режиму. Він може врятувати заряд, але пропускає
вікна зйомки та зв'язку й не гарантує виживання апарата з недостатнім живленням.

## 5. Як проходить один хід

1. Показати прогноз подій. Номер витка та наявність бурі вже відомі.
2. Дати гравцеві змінити тумблери без витрати ігрового часу.
3. Після `Next orbit` зафіксувати налаштування на цей виток.
4. Послідовно розрахувати освітлену ділянку без активних вікон,
   вікно зйомки, сеанс зв'язку й тінь.
5. Оновити заряд, пам'ять, передачу даних, холодовий стрес і журнал.
6. Якщо втрачено живлення — одразу завершити частину; інакше зарахувати повний виток.
7. Після останнього витка визначити результат. Інакше відкрити наступний хід.

Для MVP зйомка й сеанс зв'язку — непересічні вікна на освітленій ділянці,
сеанс зв'язку йде після зйомки. Тінь завершує виток. Це свідоме спрощення
розкладу, а не модель реальної географії наземної станції.

Тривалості:

```text
shadowS   = flight.orbit.periodS × flight.orbit.eclipseFraction
sunlightS = flight.orbit.periodS − shadowS
imagingS  = min(mission.imagingSPerOrbit, sunlightS)
passS     = min(mission.passSPerOrbit, sunlightS − imagingS)
idleSunS  = sunlightS − imagingS − passS
```

Такий розклад зберігає тривалість витка навіть за інших параметрів місії.
Якщо вікно скоротилося, прогноз прямо показує його фактичну тривалість.
Час усередині витка симульований; гравець не чекає півтори години.

## 6. Енергія, дані та буря

### Енергетичний баланс

Для кожного відрізка з незмінним навантаженням:

```text
loadW = baseLoadW + потужність активних на цьому відрізку систем
generationW = доступна потужність панелей, у тіні 0
chargeWh = clamp(chargeWh + (generationW − loadW) × dtS / 3600,
                 0, доступна ємність батареї)
```

Спочатку в `init` батарея повністю заряджена до доступної після пошкоджень
ємності, буфер порожній. Це нова домовленість MVP: поточний `FlightResult`
не передає залишок заряду чи дані з польоту.

Якщо за від'ємного балансу заряд досягає нуля, фіксуємо точний час відмови
і завершуємо симуляцію. Дані після цього моменту не знімаються й не передаються.
Нульовий заряд при достатній генерації сам по собі не є відмовою.
Повна деградація живлення або конструкції означає неможливість роботи вже на старті.
Надлишок генерації при повній батареї втрачається.

Передачу, що завершилася раніше за кінець сеансу через порожній буфер,
рахуємо окремим відрізком: після неї навантаження передавача відсутнє.
Прогноз використовує ту саму функцію розрахунку, що й реальний хід.

### Зв'язок і пам'ять

За відрізок зйомки виробляється `effectiveInstrumentRateMbps × dtS` мегабіт.
У пам'ять потрапляє лише вільний обсяг; втрати записуються окремо.
За сеанс передається `min(bufferMb, effectiveDownlinkMbps × passS)`.
У стані розрізняємо `bufferMb` — зайняту пам'ять і `spec.bufferMb` — її місткість.

### Сонячна буря

Пропозиція балансу для поточної місії: рівно одна буря на одному з витків 4–7.
Номер обирається один раз через `nextRandom(seed)`; наступний стан генератора
зберігається. Для коротших місій вікно обрізається до наявних витків;
якщо витків менше чотирьох, бурі немає.

Буря триває один виток: множить доступну генерацію панелей та швидкість
передачі на 0.5. Постійних пошкоджень від неї в MVP немає.
Гравець отримує попередження щонайменше за один хід і бачить її у прогнозі.
Усі ці коефіцієнти — запропоновані ігрові налаштування, не дані NASA.

## 7. Залежність від перших двох частин

Не створюємо окремий «стандартний супутник»: використовуємо `input.spec`.

- Батарея задає запас на тінь; панелі — можливість зарядитися на світлі.
- Камера задає швидкість даних, споживання та початкову роздільну здатність.
- Антена задає швидкість і вартість передачі в енергії.
- Фактичні `altKm`, `periodS`, `eclipseFraction` надходять із польоту.
- Паливо в MVP відображається за потреби, але орбітальних маневрів немає.

Роздільну здатність на фактичній висоті беремо через масштабування готової
характеристики: `spec.resolutionM × flight.orbit.altKm / spec.design.altKm`.
Це відповідає лінійній залежності вже використаної формули від висоти;
нові параметри об'єктива в спільний контракт не додаємо.

Пошкодження за системою: беремо найбільшу `severity` серед її записів,
обмежену діапазоном 0…1; повторні записи не перемножуємо.

- `power`: доступні генерація й ємність батареї множаться на `1 − severity`.
- `comms`: швидкість передачі множиться на `1 − severity`.
- `science`: швидкість отримання даних множиться на `1 − severity`.
- `thermal`: при `severity = 1` обігрів недоступний; інакше після тіні
  з обігрівом стрес зменшується на `1 − severity`.
- `structure`: при `severity = 1` апарат непрацездатний; менші значення
  не мають окремого ефекту у цій версії.
- `propulsion`: окремого штрафу немає, оскільки враховано фактично отриману
  орбіту, а маневрів у цій версії немає.

Потужність споживачів від цих коефіцієнтів не зменшуємо: пошкоджений
прилад може витрачати енергію менш ефективно. Якщо його продуктивність нульова,
автоматична робота не запускається, UI пояснює недоступність.

Усі правила цього розділу — пропозиція для інтеграції, а не вже наявна
домовленість із розробником польоту. Нові спільні поля для MVP не потрібні.

## 8. Перемога, провал і розбір

Успіх лише після завершення всіх `mission.durationOrbits` витків, коли одночасно:

- апарат не втратив живлення й не був непрацездатним на старті;
- `deliveredMb >= mission.requiredDataMb`;
- фактична роздільна здатність не гірша за `mission.requiredResolutionM`;
- фактична висота входить у `mission.altRangeKm` включно з межами.

Дострокове виконання плану даних не закінчує місію: потрібно зберегти апарат
до кінця. Холодна камера чи переповнення пам'яті самі по собі не означають програш.
За непридатної орбіти дозволяємо дограти та бачити причину невиконання місії.

У `MissionOutcome` повертаємо `success`, реально передані `deliveredMb`,
кількість повністю завершених `survivedOrbits` і
`score = Math.round(deliveredMb / 100)` для сумісності з поточним форматом очок.
Очки не замінюють прапорець перемоги: їх може мати й невдала місія.

Приклади пояснень:

- «Втрачено живлення в тіні: батареї не вистачило на базові системи й обігрів».
- «Не передано потрібний обсяг: камера виробляла дані швидше, ніж антена передавала».
- «Обсяг передано, але якість знімків не відповідає вимозі».

Кожне перемикання записуємо як рішення з унікальним id, наприклад
`orbit:turn-3-toggle-heater-2`. Відмови й втрати посилаються через `causedBy`
на реальні попередні записи: відповідні перемикання, подію бурі,
рішення `design:battery`, `design:solar`, `design:instrument`, `design:antenna`
та пошкодження з польоту, якщо вони є в переданому журналі.
Не посилаємося на вигадані id відмов польоту. Для пошкоджень без окремих
записів додаємо власну подію отриманого стану апарата й посилаємося на неї.
У журналі тільки `messageKey` і параметри; `finish().log` містить лише записи орбіти.

## 9. Три невеликі приклади роботи

### Приклад A. Зняти, передати, пережити тінь

Поточна місія, висота 400 км, середні модулі, без пошкоджень і бурі:

- батарея 60 Wh, панелі 160 W;
- камера 8 Mbps і 30 W; вікно 300 с → 2400 Mb;
- антена 10 Mbps і 30 W; до 480 с сеансу → місткість передачі 4800 Mb;
- базове споживання 20 W, обігрів 15 W;
- період близько 5545 с, тінь близько 2163 с.

Камера, передавач та обігрів увімкнені. Камера збере 2400 Mb.
Передавач скине їх за 240 с і вимкнеться до кінця сеансу.
На освітленій ділянці батарея встигає залишитися повною.
Тінь забере приблизно `(20 + 15) × 2163 / 3600 = 21.03 Wh`.
Після першого витка: заряд близько 38.97 Wh, буфер 0 Mb,
передано 2400 Mb, стрес 0. Якість знімка близько 1.342 м при вимозі 2 м.

Важлива відмінність від чинної заглушки: камера не працює в тіні.
Тому мала батарея на 30 Wh у цьому розкладі також може пережити тінь.
Не переносити автоматично старий сценарій «мала батарея завжди гине»
з тестів заглушки в нові правила.

### Приклад B. Камера перевантажує слабку антену

Ті самі умови, але антена мала: 2 Mbps. Вона скидає лише 960 Mb за сеанс.
Місткість буфера — 4000 Mb. Наведений розрахунок даних не залежить від бурі,
оскільки розглядаємо лише перші три витки; живлення справне.

1. Виток 1: знято 2400, передано 960, лишилося 1440 Mb.
2. Виток 2: ще 2400, передано 960, лишилося 2880 Mb.
3. Виток 3 із камерою: вміщається лише 1120 нових Mb,
   втрачається 1280 Mb, після передачі лишається 3040 Mb.

Альтернатива на третьому витку: вимкнути камеру й залишити передавач.
Втрат немає, буфер зменшиться з 2880 до 1920 Mb, енергії витратиться менше.
Це усуває переповнення, але за 10 витків така антена передасть максимум
9600 Mb навіть без бурі — менше цілі 10000 Mb. Керування може покращити
результат, але не усуває всі наслідки невдалої збірки.

### Приклад C. Буря та безпечний режим

Пошкодження живлення з польоту — 0.5: середні панелі тепер дають 80 W,
батарея має доступні 30 Wh. На витку з бурею генерація впаде до 40 W.
Гравець заздалегідь бачить попередження й перемикає `Safe mode`.

Камера й передавач не працюють, на світлі навантаження лише 20 W.
Батарея заряджається; у тіні працюють базові системи й обігрів.
Це дає кращий запас, ніж активна зйомка й передача під час бурі,
але за цей виток не надходить нових даних на Землю.
На наступному витку гравець вимикає режим і повертається до своєї програми.

Це приклад вибору, а не обіцянка гарантованого порятунку:
прогноз має врахувати фактичний початковий заряд і час до тіні.

## 10. Завдання розробнику orbit

### Крок 1. Логіка й дебаг

Файли: `src/core/orbit/phase.ts`, `src/core/orbit/index.ts`,
`src/core/orbit/phase.test.ts`; підключення — один рядок у `src/core/phases.ts`.

- Реалізувати `OrbitPhase<OrbitState, OrbitAction>` за чинним контрактом.
- Вхід: `OrbitInput` — місія, специфікація, результат польоту, попередній журнал.
- Вихід: `PhaseOutput<MissionOutcome>`; попередній журнал не дублювати.
- Стан: вхід, `rngState`, `tS`, завершені витки, заряд, зайнятий буфер,
  передані й втрачені дані, холодовий стрес, тумблери, номер бурі,
  статус завершення, власний журнал. Звичайні JSON-дані.
- Дії: `{ type: 'toggle', id }` і `{ type: 'tick', dtS }`.
- У покроковому MVP кнопка надсилає `tick` із `dtS = flight.orbit.periodS`.
  Решту значень, зокрема NaN та від'ємні, ігнорувати. Дробові й реальні
  часові кроки залишити для розширення; не змішувати дві моделі часу.
- `debugActions` повертає тумблери та останньою дією — наступний виток.
- Після завершення будь-які дії повертають попередній стан без змін.
- Прогноз створюється чистою функцією через той самий розрахунок витка,
  без зміни поточного стану, журналу чи генератора випадкових чисел.

Приклад використання майбутнього API, не код уже наявної реалізації:

```ts
const state = orbitPhase.init({ mission, spec, flight, log }, 42);
const withoutCamera = orbitPhase.step(state, { type: 'toggle', id: 'camera' });
const next = orbitPhase.step(withoutCamera, {
  type: 'tick', dtS: flight.orbit.periodS,
});
// next: завершено один виток, витрачено енергію, передано наявні дані.
// state і withoutCamera залишилися незмінними.
```

### Крок 2. Екран

Файли: `src/ui/orbit/OrbitScreen.tsx` та компоненти всередині цієї теки.
Пропси: стан фази й `dispatch(action)`; усі прогнози та ігрові розрахунки
надходять із ядра. Кнопка не запускає власний таймер.
Налаштування за замовчуванням: камера, передавач і обігрів увімкнені,
безпечний режим вимкнений, холодовий стрес 0.

### Крок 3. Передача інтегратору

- Попросити додати англійські ключі повідомлень у `src/data/texts.en.json`.
- Запропоновані коефіцієнти бурі та холоду винести в погоджені дані
  (наприклад, `src/data/orbit-rules.json`); не дублювати їх у UI.
- Інтегратор підключає екран у загальну оболонку `App.tsx`.
- `contracts.ts`, `game.ts`, `physics.ts`, чужі фази та залежності не змінювати.
- `sim.ts` і консорціум зараз викликають `stubOrbit` напряму:
  заміна експорту в `phases.ts` сама по собі їх не оновить.
  Для нової перевірки балансу потрібен окремий погоджений бот керування
  й інтеграція; не представляти результати старої заглушки як баланс нового режиму.
- Старі інтеграційні тести можуть очікувати автоматичну смерть малої батареї.
  Показати інтегратору цю зміну моделі; чужі тести не послаблювати мовчки.

## 11. Критерії готовності

- Частина проходиться від отримання `OrbitInput` до `MissionOutcome` через дебаг.
- Наступний виток змінює стан лише після дії гравця, прогноз збігається з результатом.
- Є перевірені сценарії A і B, бурі, безпечного режиму та відновлення після холоду.
- Повний / порожній буфер, нульовий час вікон і повна деградація систем
  обробляються без NaN, від'ємних ресурсів та передачі неіснуючих даних.
- Відмова посеред витка зупиняє дані й час у точці відмови;
  незавершений виток не входить у `survivedOrbits`.
- Зібрати достатньо даних, але не пережити всі витки — провал.
- Передати достатньо даних із непридатною якістю чи орбітою — провал.
- Кожна відмова має непорожній `causedBy`, усі посилання існують,
  id унікальні в межах забігу, тексти повідомлень доступні за ключами.
- `step` не мутує стан; однакові вхід, seed та дії дають однаковий результат;
  стан і результат переживають JSON round-trip.
- Для приймання реалізації пройдено `npm run typecheck`, `npm test`,
  `npm run build` та ручний прохід до розбору.

## 12. Що тут запропоновано самостійно

Для конкретного, придатного до передачі завдання додано: один виток на хід,
автоматичні робочі вікна, повний початковий заряд, порожній початковий буфер,
умовний холодовий стрес, правила пошкоджень, одну прогнозовану бурю та її
коефіцієнти, критерій придатності фактичної орбіти й приклади чисел.
Це оформлені пропозиції MVP; вони ще не реалізовані й не перевірені
балансуванням гри. Вибір цієї версії потребує звірки з інтегратором перед
зміною спільних даних, тестових очікувань та логіки консорціуму.
